## What was done

Submitted a manual `rust-verify` workflow against pdftract main, per the bead scope:

```yaml
spec:
  workflowTemplateRef:
    name: rust-verify
  arguments:
    parameters:
    - name: repo
      value: "https://git.ardenone.com/jedarden/pdftract.git"
    - name: revision
      value: "main"
    - name: github-repo
      value: "jedarden/pdftract"
```

Deviations from the bead's example submission (the example would have failed as written):

1. **Parameter name is `revision`, not `ref`.** The live template's parameters are `repo`,
   `revision`, `test-args`, `builder-image`, `github-repo`. Submitting `ref` would be rejected
   as an unknown argument.
2. **`repo` needs the full HTTPS URL.** `git clone git.ardenone.com/jedarden/pdftract` (no
   scheme) is parsed as a local path and fails outright. HTTPS is also required because the
   template's credential helper is keyed on `credential.https://git.ardenone.com.helper`.
3. **There is no `git-clone` container.** The `verify` template is a single container; the
   clone runs inside its bash script and its output is redirected to `/tmp/verify-output`,
   which the template persists as the workflow `output` parameter. Clone evidence therefore
   comes from the workflow object's output parameter (and from the pod surviving past the
   clone phase — a clone failure exits 1 within seconds), not from `kubectl logs -c git-clone`.
4. **Secret name is `forgejo-webhook-token`** (key `token`), not the `forgejo-ci-token` name
   used in the bf-5ig30 note — the secret was renamed when the sealing work (bf-1bbkdv) landed.
   The live template and live pod both reference `forgejo-webhook-token`.

